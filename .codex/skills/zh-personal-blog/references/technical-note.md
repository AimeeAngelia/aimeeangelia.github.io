# 技术笔记路线

适用于部署、配置、排错、开发环境、软件体验和可复现操作。

## 组织材料

优先确认这些信息；没有的不要补造：

- 为什么会做这件事，以及最初看到了什么现象；
- 系统、软件、版本、网络或账号环境；
- 实际错误、日志、截图和失败尝试；
- 最终有效的操作及其适用边界；
- 仍未解决的问题和后续变化。

## 推荐写法

- 开头先讲这次具体经历或问题。只有理解操作确实需要时才补背景。
- 按“遇到问题的顺序”或“读者执行的顺序”选择一种主线，不要来回切换。
- 把作者实际执行的操作与一般建议分开。使用“我这里”“当前环境”“可能”准确限定范围。
- 命令、配置和日志保持精确；不得生成看似合理但未运行过的输出。
- 解释关键选择，例如为什么不用另一个工具、为什么固定版本、为什么先备份。普通点击步骤可以简写。
- 如果来源会变化，链接到官方文档并写明文章验证时的版本或日期。
- 截图用于证明界面、报错或结果，不用长段文字重复截图中显而易见的内容。

## 结构不是模板

常见文章可以是：

```text
发生了什么
当前环境或结果
有效步骤
途中踩坑与原因
仍需注意的限制
```

这只是可选顺序。一次很小的修复可以只有问题、原因和三步操作；一次长期搭建记录可以按组件拆节。

## 结尾

优先停在验证结果、仍存在的限制、下次会怎么做或一条真实经验。不要为了结束文章重新概括所有章节，也不要把一次配置上升成普遍的人生道理。

后续状态发生变化时，可以追加带日期的 `Update`，不必重写成一篇仿佛一次完成的文章。
